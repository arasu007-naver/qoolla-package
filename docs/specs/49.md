# 진입 재생(fastforward)에 컷·step 사이 180ms 간격 넣기

## 배경과 목적
학생 앱이 실황 수업 화면에 들어오면 마지막 진행 지점(lastcut, guide `{studyIdx, step}`)까지 칠판을 따라잡아야 합니다. 그래야 선생님 칠판(canvas board)과 학생 앱 칠판(canvas screen)의 내용이 같아집니다. 이 따라잡기는 `src/player.ts`의 **fastforward**(docs/COMPONENTS.md: `fastforward`: `src/player.ts`)가 맡습니다.

현재 코드에서 확인한 내용:
- 리셋 컷(CLEAN/CLEAN_SCENE/CLEAR)과 BACKGROUND 컷은 `runCut` 뒤에 기다리지 않고 바로 다음 컷으로 넘어갑니다(`continue`).
- `runCurtains(startIdx)` 뒤에도 기다리지 않습니다.
- prologue 뒤 480ms, main 뒤 420ms, epilogue 뒤 480ms, MAGNIFY와 runMagnifier 뒤 600ms를 기다립니다. 다만 "각 컷, 각 step 사이에 반드시 간격이 있다"는 규칙은 코드에 없습니다.

그래서 진입 재생이 '재생'이 아니라 한 번에 모두 실행된 것처럼 보입니다. 이 작업에서는 사람이 순서를 알아볼 수 있는 180ms 간격(`await sleep(180)`)을 각 컷 사이와 각 step(prologue, main, epilogue) 사이에 넣습니다.

## 범위
### 하는 것
- `src/player.ts`에 상수 `CATCH_UP_GAP_MS = 180`을 추가하고 export합니다.
- `fastforward`에서 칠판을 바꾸는 콜백(runCurtains, runCut, runPrologue, runEpilogue, runMagnifier)을 실행한 뒤마다 `await sleep(CATCH_UP_GAP_MS)`를 추가합니다. 이 sleep은 `callbacks.sleepFn ?? defaultSleep`입니다.
- 빌드(`npm run build`)로 `dist/`를 다시 만들어 커밋에 포함합니다.
- `package.json`의 `version`을 `1.5.0`에서 `1.6.0`으로 올립니다.
- README와 docs/COMPONENTS.md의 fastforward 설명에 180ms 간격 규칙을 한 줄 추가하고, `CATCH_UP_GAP_MS` 항목을 추가합니다.

### 하지 않는 것
- `playToPoint`의 순차 재생 루프(수업 중 실시간 진행), `runNext`, `runAt`의 대기 시간은 바꾸지 않습니다. 단, `playToPoint`가 역방향, refresh, sync 때 `fastforward`로 넘기는 경로는 fastforward의 새 동작을 그대로 따릅니다.
- 기존 대기(480/420/480/600ms)는 지우거나 줄이지 않습니다.
- 재생 시작점(`findNearestCleanBefore`), step 범위, `refresh` 처리, `syncCanvasObjects`, `onStateChange` 순서와 의미는 바꾸지 않습니다.
- 메시지 형식과 다른 export의 시그니처는 바꾸지 않습니다.

## 변경할 동작
`fastforward(cutContents, targetGuide, callbacks)`의 sleep 함수를 `sleep = callbacks.sleepFn ?? defaultSleep`로 둡니다.
1. `callbacks.runCurtains`가 있으면 `await runCurtains(startIdx)`를 실행하고, 이어서 `await sleep(CATCH_UP_GAP_MS)`를 실행합니다.
2. 루프 안에서 리셋 컷(`isResetCut`)이나 BACKGROUND 컷이면 `await runCut(...)`, `await sleep(CATCH_UP_GAP_MS)` 순서로 실행한 뒤 `continue`합니다.
3. MAGNIFY 컷이면 `await runCut(...)`, `await sleep(600)`(기존), `await sleep(CATCH_UP_GAP_MS)` 순서로 실행합니다.
4. step 루프에서 각 step은 다음 순서로 실행합니다.
   - prologue: hasP이고 runPrologue가 있을 때 `runPrologue` → `sleep(480)` → `sleep(CATCH_UP_GAP_MS)`
   - main: `runCut` → `sleep(420)` → `sleep(CATCH_UP_GAP_MS)`
   - epilogue: hasE이고 runEpilogue가 있을 때 `runEpilogue` → `sleep(480)` → `sleep(CATCH_UP_GAP_MS)`
   - 실행하지 않는 step(멤버가 없는 prologue/epilogue)에서는 sleep도 하지 않습니다.
5. `runMagnifier`가 있으면 `runMagnifier` → `sleep(600)`(기존) → `sleep(CATCH_UP_GAP_MS)` 순서로 실행합니다.
6. 그 결과, fastforward 안에서 칠판을 바꾸는 콜백 두 개가 연달아 실행될 때 그 사이에 언제나 `sleep(180)` 호출이 한 번 이상 있습니다.

## API 계약
외부 API(HTTP/GraphQL)는 없습니다. 패키지 공개 계약은 다음과 같습니다.
- 새 export: `export const CATCH_UP_GAP_MS = 180;`
- `fastforward(cuts, targetGuide, callbacks): Promise<PlayerState>`의 시그니처와 반환값은 그대로입니다. 바뀌는 것은 위 '변경할 동작'의 sleep 호출 순서뿐입니다.
- `ScriptPlayerCallbacks.sleepFn`이 주어지면 180ms 간격에도 그 함수를 씁니다.
- 버전: `@qoolla/script-parser` 1.6.0(git 태그 `v1.6.0`)

## 수용 기준
1. `package.json`의 `version`이 `1.6.0`입니다.
2. `src/player.ts`와 `dist/index.d.ts`(또는 `dist/player.d.ts`)에 `CATCH_UP_GAP_MS`가 export되어 있고 값이 180입니다.
3. `npm run build`가 오류 없이 끝나고, 커밋된 `dist/player.js`·`dist/player.mjs`에 새 sleep 호출이 반영되어 있습니다.
4. sleepFn을 로그 mock으로 넘기고 `[BACKGROUND(0), ADD a(1), CLEAN(2), ADD c(3), ADD d(4)]`에 `fastforward(cuts, {studyIdx:4, step:'main'}, cb)`를 호출합니다(prologue/epilogue 없음, runCurtains 있음). 이때 호출 로그는 `runCurtains(2)`, `sleep180`, `runCut CLEAN`, `sleep180`, `runCut c`, `sleep420`, `sleep180`, `runCut d`, `sleep420`, `sleep180` 순서이고, ADD a와 BACKGROUND는 실행되지 않습니다.
5. 리더 L의 prologue와 epilogue가 모두 있는 컷 하나에 `fastforward(cuts, {studyIdx:0, step:'epilogue'}, cb)`를 호출하면 로그는 `runPrologue`, `sleep480`, `sleep180`, `runCut`, `sleep420`, `sleep180`, `runEpilogue`, `sleep480`, `sleep180` 순서입니다.
6. 4번과 5번에서 칠판을 바꾸는 콜백(runCurtains/runCut/runPrologue/runEpilogue/runMagnifier) 두 개가 `sleep180` 없이 연달아 호출되는 경우가 없습니다.
7. MAGNIFY 컷은 `runCut` 뒤에 `sleep600`, `sleep180` 순서로 기다립니다.
8. `{studyIdx:k, step:'refresh'}`이면 지금처럼 k번 컷의 main을 실행하지 않습니다. 반환 상태는 `{currentIdx:k, cutSequence:'refresh'}`입니다.
9. `playToPoint`의 순차 재생(역방향·refresh·sync가 아닌 경우)에서는 `sleep180`이 호출되지 않아, 호출 로그가 변경 전과 같습니다.
10. `runNext`와 `runAt`의 호출 로그가 변경 전과 같습니다.
11. `npx tsc --noEmit`(또는 빌드의 타입 검사)이 통과합니다.

## 가정
- 요구사항의 '추가'를 기존 대기(420/480/600ms)를 그대로 둔 채 180ms를 더하는 것으로 해석했습니다.
- 진입 재생은 student-app이 이 패키지의 fastforward로 하고 있으므로, 간격 규칙은 fastforward에만 넣습니다.
- 현재 패키지에는 테스트 러너가 없습니다. 수용 기준은 mock sleepFn으로 호출 순서를 기록하는 임시 스크립트나 테스트로 확인하면 되고, 테스트 러너 추가는 필수가 아닙니다.
